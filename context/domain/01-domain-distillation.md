# Domain Distillation — BikeFit

> Product of a DDD discovery pass over the **existing source documents and code**.
> The deliverable is a **map of the domain**, not code. Nothing here proposes an
> implementation; Step 5 only ranks where a model would pay off most.
> Discovery → Ubiquitous Language → subdomain classification → aggregate
> candidates → model-vs-code divergence → refactor ranking.
>
> Sibling document: [[02-invariant-aggregate-refactor]] takes the **#1 pick from
> Step 5** (the `FittingSession` lifecycle) down to a concrete aggregate + repository
>
> - migration design. This document is the wider map that puts that pick in context
>   and surfaces the runner-up (angle / verdict trust boundary).

## Step 3 — Aggregate candidates and their invariants

For each candidate: the rule that **must always be true**, its source, and whether
the code **enforces**, merely **declares**, or **ignores** it.

### Candidate A — `FittingSession` (aggregate root)

_Consistency boundary for the session lifecycle; `AnalysisResult` is an entity
inside it (0..1, cascade-deleted, never loaded alone —
`initial_schema.sql:53`)._

| Invariant                                                                                                                                                 | Source                                                                                                                                                                                          | Status                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A-1** Lifecycle is monotonic `queued → processing → {completed \| failed}`; transitions are legal-source-state only; `completed`/`failed` are terminal. | `initial_schema.sql:16-17`; F-02 plan "Desired End State" (`archive/2026-05-31-async-job-pipeline/plan.md:31-37`); guards at `start.ts:34`, `results.ts:48`, `recommend.ts:47`, `analyze.ts:70` | **IGNORED at storage.** `CHECK` enforces the _alphabet_ not the _grammar_ (`completed → queued` passes). Each route does a non-atomic read-then-write; the `UPDATE` carries no `AND status = <expected>` (`start.ts:43-47`, `results.ts:72-76`).                                                                                                                         |
| **A-2** A session is `completed` **iff** exactly one `analysis_results` row exists, both written atomically.                                              | `sessions/[id].astro:50-53` ("_A `completed` session should always have a results row_"); PRD US-01 (`prd.md:50-53`)                                                                            | **IGNORED.** `results.ts:59-76` inserts the row, then flips status in a **second** statement; comment `results.ts:78-82` accepts the orphan. No `UNIQUE(session_id)` — `initial_schema.sql:82` is a plain index → a race writes two rows → `[id].astro:49` `.maybeSingle()` errors permanently.                                                                          |
| **A-3** Every started analysis reaches a **terminal, human-readable** state — none stuck in `processing`/`queued` forever; no silent failure.             | `prd.md:40`; test-plan Risk #6 (`test-plan.md:54,76`)                                                                                                                                           | **DECLARED / faked.** `effectiveSessionStatus` (`session-display-status.ts:24-30`) reconciles **at render time only** — "_the stored row is never written_" (`session-display-status.ts:13`). A server-side reaper is "deliberately not built" (`test-plan.md:874-876`). `results.ts:97-102` swallows the failed `→ failed` write, pinned by `_results.test.ts:120-130`. |
| **A-4** `status` and results are written **only by the server** (`service_role`); the browser is untrusted.                                               | `initial_schema.sql:44-46` ("_performed by the pipeline worker via `service_role`_")                                                                                                            | **VIOLATED BY DESIGN.** `VideoAnalyzer.tsx:99-112` has the browser compose the failure message and POST the `failed` transition; `VideoAnalyzer.tsx:120-121` has the browser decide a 409 means "carry on".                                                                                                                                                              |

### #1 pick — `FittingSession` lifecycle, and why

It is the **only** candidate that is simultaneously **the most central** — the
North Star outcome and the "no silent errors" guardrail are both literally
statements about `status` — and **the least genuinely enforced**: there is no
atomic transition in the system, "reaches a terminal state" is a render-time
illusion over a row that stays `processing` forever, `results.ts` returns
`{ ok: true }` on a failed failure-write, and the browser decides what a 409
means. Every other Core area is in better shape: privacy (UL-18) is airtight _by
the absence of a column_; the angle geometry and reference bands (C-1, C-2) are
unit-tested and single-sourced; iterative progression (E) has no feature yet to
break. `FittingSession` is exactly where core-ness and fragility intersect —
which is why [[02-invariant-aggregate-refactor]] already carries it forward into a
full aggregate + `advance_fitting_session` compare-and-set + thin-route design.

### #2 pick — the angle / verdict trust boundary (this document's addition)

`02` treats the angle rules as INV-8/INV-9 and correctly notes they are
"already covered by tests and single-sourcing" — but that is only true on the
_write and prompt_ path. The **read path** verdict shown to the user
(`sessions/[id].astro` → `angleVerdict`) is computed from `reference_min/max`
values the **browser** wrote into `analysis_results.body_angles`, never
re-validated against server-side `ANGLE_REFS` (D-09, C-3). A session whose
persisted bands were tampered, or simply written by an older client with the
pre-2026-09-02 bands, will render "In range / Outside range" pills that
contradict the authoritative reference frame — directly undermining the
Success Criterion that recommendations "fall within accepted reference ranges".
The fix is small (re-derive the verdict server-side from `ANGLE_REFS` keyed by
angle name; treat the persisted bounds as display sugar) and does not need the
full aggregate machinery of #1.

## Summary

BikeFit is a self-service gravel bike-fitting web app: a logged-in cyclist
uploads a short side-view clip, the **browser** runs pose estimation plus two
LLM calls to measure five joint angles and turn them into plain-language
adjustment advice, and every attempt is saved to session history. This document
maps the domain from the PRD, roadmap, the authoritative reference-angle doc, and
the code; it names 27 Ubiquitous-Language terms, and for each says whether it
lives in code or is model-only. The Core subdomains are **angle / reference-frame
correctness**, **recommendation generation**, the **FittingSession lifecycle**,
and the **iterative fitting progression** — with privacy ("process and discard")
as a hard Core constraint that the code satisfies structurally by never having a
video column to write. Five aggregate candidates emerge; the one genuinely
hardened piece of the system is `RateLimitWindow` (an atomic, privilege-locked
RPC), which is the pattern the rest should copy. Fifteen model-vs-code
divergences are catalogued — the sharpest being that the "iterative cycle" that
the PRD says is the whole point of session history has **no code representation
at all** (D-01), the "no silent errors" guardrail is contradicted by a route that
returns `{ ok: true }` on a failed write (D-03), and the "terminal state"
guarantee is faked at render time while the stored row stays `processing` forever
(D-04). The refactor ranking puts the **`FittingSession` lifecycle** at #1 (most
core, least enforced — already carried forward by
[[02-invariant-aggregate-refactor]]) and the **angle / verdict trust boundary**
at #2 (the read-path verdict is computed from browser-authored reference bounds,
never re-checked against the authoritative bands — a small, high-value fix this
map surfaces that `02` does not).
