# Research: Abuse & resource protection (test-plan Phase 3)

**Date**: 2026-09-05T12:58:13+02:00
**Researcher**: maro
**Git Commit**: e1f60c520157a84ef01e7f101bd6f579165b6e8b
**Branch**: master
**Repository**: mjedrasz/bikefit

## Research Question

Ground `context/foundation/test-plan.md` §3 Phase 3 ("Abuse & resource protection", Risks #3 and #4) before planning. Per `context/changes/testing-abuse-resource-protection/change.md`, the plan needs: the full request path for the vision (`/api/analyze`) and recommendation (`/api/sessions/[id]/recommend`) routes; where a rate limiter would sit; the current server-side payload caps (if any); the provider-error branch (4xx/5xx/403/451 handling); and how the vision route's timestamp-schema output contract is actually enforced on the model's response — including whether raw model text ever escapes the boundary.

## Summary

**Risk #3 (resource/rate-limiting) — genuinely greenfield feature work**, confirmed by both codebase and historical-context research:

- **No rate limiting, throttling, or IP tracking exists anywhere in `src/`** (`grep -rniE "rate.?limit|throttle|abuse" src/` → zero hits). The app has zero Cloudflare data bindings beyond `ASSETS` (no KV, D1, Durable Objects, or Rate Limiting binding in `wrangler.jsonc`), so any limiter is built from scratch, not activated from existing infrastructure.
- **Session-binding is already done.** Contrary to the test-plan's Risk #3 wording ("the vision route not scoped to an owned session"), Phase 2 already closed this: `analyzeRequestSchema` requires `session_id: z.uuid()` (`src/lib/schemas.ts:23`) and `src/pages/api/analyze.ts:26-50` runs an RLS-backed ownership + `status === "processing"` pre-check before calling the vision LLM, with an inline comment explicitly citing budget-burn abuse as the reason. **This part of Risk #3 needs a test, not new code.**
- **A server-side payload cap already exists but is stale/misdescribed.** `analyzeRequestSchema.video.max(140_000_000)` chars (`src/lib/schemas.ts:22`) was added reactively during the original pipeline's implementation review (finding F5, `context/archive/2026-05-28-ai-analysis-pipeline/reviews/impl-review.md`), sized only to "match the client's 100MB cap" — never independently reasoned about for abuse/cost purposes. It is also enforced **after** the full body is buffered and JSON-parsed (`context.request.json()` runs before schema validation in `analyze.ts`), so the cap doesn't prevent the memory/CPU cost of buffering an oversized body — it only rejects afterward. The test-plan's "no server-side payload caps" framing for Risk #3 is therefore imprecise: a cap exists, but it doesn't do the resource-protection job a cap should do.
- **`recommendRequestSchema.body_angles` has NO array-length or field-length cap at all** (`z.array(bodyAngleSchema).min(1)`, `schemas.ts:27`) — an authenticated, owning caller can submit an unbounded array straight into the recommendations prompt. This is the other route Phase 3 must cover; it currently has _no_ size guard of any kind, not even a stale one.
- **No status-code branching exists for provider errors.** `src/lib/services/llm.ts:101-105` and `:159-163` both use one `if (!response.ok)` branch for every non-2xx status (429/500/403/451 alike) — confirmed by the existing `it.each([429, 500, 403, 451])` contract-test corpus (`llm.test.ts:27,97`), which already proves _uniform_ graceful degradation (a fixed plain-language error, no upstream text leaked) but never _distinct_ handling per status. If Phase 3's risk-response wording ("degrades to a clean plain-language error") is read as requiring differentiated messaging per status class, that is new work; if it's read as "never a stack trace/silent hang," it's already proven and just needs the new payload/rate-limit paths added to the same corpus pattern.
- **Recommended mechanism (external research, Cloudflare docs verified 2026-09-05):** a Postgres/Supabase atomic-upsert counter (`INSERT ... ON CONFLICT DO UPDATE ... RETURNING`, invoked via `supabase.rpc(...)` since supabase-js's `.update()` can't express `count = count + 1`) is the best MVP fit — it reuses the app's only real datastore, ships as a normal RLS-guarded migration matching project conventions, and is testable today with the existing `vi.mock("@/lib/supabase")` pattern with zero new test infrastructure. Cloudflare's native Rate Limiting binding is GA (since 2025-09-19) and works locally under `astro dev`/`wrangler dev` on this repo's adapter version, but its own docs call it "permissive, eventually consistent... not an accurate accounting system" (per-PoP, not global) and it would need a `workerd`/Miniflare test runtime the project's Vitest `unit` project doesn't have — good as an optional coarse _second_ layer, not a substitute for a real per-user cap. KV and Durable Objects are both worse fits (KV: 60s+ propagation lag, 1-write/sec/key limit, Cloudflare's own docs steer away from this use case; Durable Objects: a whole new primitive/billing dimension for a problem Postgres already solves for free).
- **Payload-size enforcement needs to move earlier.** Cloudflare's own best-practices docs recommend checking `Content-Length` and/or streaming-with-a-byte-counted-abort _before_ calling `.json()`/`.text()`, specifically to avoid buffering a body you're going to reject (Workers have a 128MB memory ceiling; the platform's own outer limit is 100MB on Free/Pro plans, close to this app's existing 140M-char/~105MB cap). This is a small, independently testable helper (works fine against a plain Node `Request`/`ReadableStream` in the existing `unit` Vitest project — no Cloudflare runtime needed).

**Risk #4 (prompt-injection / output-contract) — the boundary is already strict for the vision path; the gap is entirely on the prompt-defense and probe side:**

- **The vision output contract IS a genuine hard boundary today**, confirmed by full trace of `src/lib/llm-response.ts` and `src/lib/services/llm.ts:113-125`: content that fails `JSON.parse` throws, content that fails `timestampListSchema.safeParse` throws, and the only success path returns Zod's own sanitized `.data` — never the raw parsed JSON, never raw model text. No prompt-injection probe is needed to _prove_ this exists as code; it already does, and it's already contract-tested (§6.3 corpus, Phase 2).
- **The recommendations path is a _weaker_ boundary** — worth flagging even though Risk #4 is framed around the vision route: `generateRecommendations` (`llm.ts:179,187`) checks `safeParse(...).success` as a shape gate but then returns the **pre-parse** `result.recommendations as Recommendation[]`, not Zod's `.data`. Extra, unschema'd properties on a recommendation item survive validation and reach the DB write unstripped (though nothing currently renders them, since the results page only reads `.adjustment`/`.rationale`). If Phase 3's "hard output-contract boundary" is meant to cover both LLM call sites (the change.md's Risk #4 wording names only "the vision route"), this is a concrete finding to plan against.
- **`raw_llm_response` is write-only in the current app** — never read back, never rendered (no `dangerouslySetInnerHTML`/`set:html` anywhere in the repo), never used in control flow. The standing side-obligation from test-plan.md §2 ("research should still confirm error bodies and `raw_llm_response` do not echo secrets") is now closed: full trace confirms no secret/upstream-body leakage anywhere in the LLM boundary, route wrappers, or the `raw_llm_response` storage path.
- **No prompt-injection defensive framing exists** in either system prompt (`ANALYZE_VIDEO_SYSTEM_PROMPT`, `llm.ts:17-29`; `buildRecommendationsSystemPrompt`, `recommendations-prompt.ts:22-72`) — no "ignore in-video text/instructions" framing. This is a known, already-tracked gap, not a new finding. Whatever mitigates it today is downstream schema enforcement only (confirmed strict, above), not prompt-level defense. The adversarial probe set the change.md calls for is genuinely new work with no existing corpus to build on.

## Detailed Findings

### 1. Request path — `/api/analyze` and `/api/sessions/[id]/recommend`

- **`src/pages/api/analyze.ts` (61 lines), full flow**: auth check (`:10-12`, 401 if no `locals.user`) → `context.request.json()` (`:14-19`, malformed JSON → 400, **no `Content-Length` check first**) → `analyzeRequestSchema.safeParse` (`:21-24`, invalid → 400) → session ownership pre-check (`:26-50`): `.from("fitting_sessions").select("id, status").eq("id", session_id).maybeSingle()` → query error → 500; no row → 404; `status !== "processing"` → 409 → `analyzeVideo(video)` call (`:52-59`), errors caught to a fixed 500 string, upstream detail to `console.error` only. Inline comment at `:31-35` explicitly documents the session-binding as a fix for "Risk #5 — `/analyze` was not session-scoped, so any authed user could burn vision-model budget on any blob," mirroring `recommend.ts`'s pre-check.
- **`src/pages/api/sessions/[id]/recommend.ts` (57 lines)**: same shape, but the ownership pre-check (`:21-35`) runs **before** body parsing (order differs from `analyze.ts` — recommend's session id comes from the URL path param, analyze's from the body). Body validated against `recommendRequestSchema` (`:37-47`) after the pre-check.
- **Ownership is entirely RLS-delegated, not application-filtered.** Neither handler's Supabase query includes an explicit `user_id` predicate; both rely on the request-scoped (cookie-bound, non-service-role) client from `src/lib/supabase.ts:9` plus `FORCE ROW LEVEL SECURITY` + the `sessions_select_own` policy (`auth.uid() = user_id`) on `fitting_sessions` (`supabase/migrations/20260526120000_initial_schema.sql:31-37`). A cross-user session id simply returns no row, mapped to 404.
- **`src/middleware.ts` (26 lines)**: resolves `context.locals.user` on every request unconditionally, then redirects unauthenticated _page_ requests matching `PROTECTED_ROUTES = ["/dashboard", "/sessions"]` (`:4`). Neither `/api/analyze` nor `/api/sessions/[id]/recommend` matches those prefixes — both API routes are excluded from the middleware-level gate; their auth enforcement is entirely handler-local (`if (!context.locals.user)`). **No rate limiting, throttling, IP tracking, or request counter exists in this file or anywhere in `src/`.**
- **`src/lib/schemas.ts` (41 lines) — every constraint, exhaustively**:

  | Schema                   | Field                                                                      | Constraint                                                                        |
  | ------------------------ | -------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
  | `analyzeRequestSchema`   | `video`                                                                    | `z.string().min(1).max(140_000_000)` — **the only size-capped field in the file** |
  | `analyzeRequestSchema`   | `session_id`                                                               | `z.uuid()`                                                                        |
  | `recommendRequestSchema` | `body_angles`                                                              | `z.array(bodyAngleSchema).min(1)` — **no `.max()`**                               |
  | `bodyAngleSchema`        | `name`/`unit` (strings), `value`/`reference_min`/`reference_max` (numbers) | **no bounds at all**                                                              |
  | `createSessionSchema`    | `video_filename`                                                           | `min(1)`, **no max**                                                              |
  | `createSessionSchema`    | `video_duration_s`                                                         | `.positive()`, **no max** (client caps at 15s, server does not re-enforce)        |
  | `recommendationSchema`   | `adjustment`, `rationale`                                                  | **fully open-ended strings**                                                      |
  | `resultsPayloadSchema`   | `raw_llm_response`                                                         | `z.string().optional()` — **zero constraints**                                    |
  | `resultsPayloadSchema`   | `error_message`                                                            | `z.string()` — **no max**                                                         |

- **Client-side caps are UI-only and enforced once, in a different component than the one that POSTs.** `src/components/VideoUpload.tsx:24-26,59-80` — `MAX_SIZE = 104_857_600` (100MB), `MAX_DURATION = 15`s — checked at file-selection time. The actual POST happens later in `src/components/VideoAnalyzer.tsx:174-178`, which receives the already-validated `File` as a prop and never re-checks it. A direct POST to `/api/analyze` (bypassing `VideoUpload.tsx`) can submit up to the schema's 140,000,000-char ceiling — looser than the client's 100MB limit once ~33% base64 inflation is factored in, so the server "cap" is not actually a tight backstop of the client cap.
- **No `Content-Length` check, no streaming/early-abort, no MIME/content sniffing anywhere.** The only gate on `/api/analyze`'s video is the zod `.max()` char count, checked **after** `context.request.json()` has already fully buffered and parsed the body.

### 2. Provider-error branch (`src/lib/services/llm.ts`)

- **Single catch-all for every non-2xx status**, both call sites: `analyzeVideo` (`:101-105`) and `generateRecommendations` (`:159-163`) each do `if (!response.ok) { console.error(...status, await response.text()); throw new Error(<fixed string>); }`. `response.status` reaches `console.error` (server-side only) but is never inspected in a conditional — 429/500/403/451 all take the identical branch.
- **Every thrown message is a hardcoded literal, audited exhaustively** — no interpolation of upstream text or model completions anywhere. The module's own header comment (`:12-15`) states this is deliberate: "A direct API caller must never see OpenRouter's body or the raw (possibly huge/sensitive) completion." Route-layer wrappers (`analyze.ts:52-59`, `recommend.ts:49-56`) repeat the same discipline one layer up — no `err.message` in any Response body.
- **Existing contract-test corpus already proves uniform graceful degradation** across 429/500/403/451: `llm.test.ts:27,97`, `it.each([429, 500, 403, 451])` against the same fixed-string assertion per suite, plus an explicit non-leak assertion (`:89-93`, injects `"secret upstream reason"` into a mocked 500 body, asserts it never appears in the thrown message). **There is no code and no test that treats 403/451 _differently_ from 429/500** — `test-plan.md:375` already documents this as intentional current scope (one row: "`!ok` — 429/500/403/451" → one fixed message). Confirm with the planner whether Phase 3 needs _differentiated_ status handling (new work) or just needs the new rate-limit/payload-cap failure paths folded into this same corpus pattern (no differentiation needed).

### 3. Output-contract boundary (Risk #4)

- **Vision path — hard boundary, confirmed**: `src/lib/llm-response.ts` (38 lines, pure, no I/O) defines `timestampItemSchema`/`timestampListSchema`. Traced through `llm.ts:113-125`: JSON-parse failure → throw (`:117`); schema failure → throw (`:122`); success → return `result.data` (Zod's sanitized output, `:125`), **never** the raw parsed JSON. No path lets schema-failing content get used, logged into a response, or passed downstream unvalidated.
- **Recommendations path — a weaker, shape-only gate**: `llm.ts:179,187` checks `safeParse(...).success` but returns the **pre-parse** `result.recommendations as Recommendation[]` (a type cast, not Zod's `.data`). Extra unschema'd properties on an item survive into the `analysis_results.recommendations` JSONB write. Currently inert (the results page only reads `.adjustment`/`.rationale`, `sessions/[id].astro:83-84`, via auto-escaping `{}` — no `dangerouslySetInnerHTML`/`set:html` anywhere in the repo), but a real gap relative to the vision path's stricter behavior. Change.md's Risk #4 wording names only "the vision route" — worth confirming with the planner whether this should be in scope too.
- **`raw_llm_response` full trace, write-only**: produced `llm.ts:182-188` (only type-checked as `typeof ... !== "string"`, no length/content check) → `recommend.ts:50-51` (passed straight to the browser) → `VideoAnalyzer.tsx:298-300,312` (client re-submits it verbatim to `/results`) → `results.ts:22` (`resultsPayloadSchema.safeParse`, no constraint beyond "is a string") → DB write (`results.ts:59-64`, unbounded `TEXT` column, `supabase/migrations/20260526120000_initial_schema.sql:56`). **Never read back**: `sessions/[id].astro:45-47` is the only display query and explicitly projects `"recommendations, body_angles"` only — confirmed via repo-wide grep with zero other reads of that column. This closes the standing test-plan §2 side-obligation ("research should still confirm error bodies and `raw_llm_response` do not echo secrets") — no leakage found anywhere in the traced path.
- **No prompt-injection defensive framing** in `ANALYZE_VIDEO_SYSTEM_PROMPT` (`llm.ts:17-29`, quoted in full by the sub-agent report) or `buildRecommendationsSystemPrompt` (`recommendations-prompt.ts:22-72`) — no instruction to disregard in-video text/QR/overlay content. Mitigated today only by the downstream schema enforcement above, not by prompt-level defense. This is an already-tracked gap (`test-plan.md:52`; `testing-llm-and-ownership/plan.md:120` explicitly deferred it here), not new.

### 4. Rate-limiting mechanism options (external research)

All claims below verified against Cloudflare/Supabase docs on 2026-09-05; see Code References for URLs.

- **Cloudflare native Rate Limiting binding — GA since 2025-09-19.** Config shape is a top-level `ratelimits` array in `wrangler.jsonc` (not the pre-GA `unsafe.bindings` syntax), requires Wrangler ≥4.36.0 (repo has `^4.90.0`, satisfied). Only one algorithm — `"simple"` (token count over a `period` that must be exactly 10 or 60 seconds) — and Cloudflare's own docs call it "permissive, eventually consistent, and intentionally designed to not be used as an accurate accounting system," enforced **per Cloudflare data-center location**, not globally. Works locally under both `wrangler dev` and plain `astro dev` on this repo's adapter version (`@astrojs/cloudflare` v13 removed `Astro.locals.runtime.env`; bindings are read via `import { env } from "cloudflare:workers"` instead — a version-specific gotcha for this codebase). Good as an optional coarse outer layer; not precise enough to be the only per-user gate, and not exercisable in the project's current `unit` Vitest project (plain Node, no Miniflare/`workerd`) without new test infrastructure.
- **KV counters — not recommended.** Cloudflare's own docs: writes may take "up to 60 seconds or more" to propagate globally, and same-key writes are capped at 1/second ("If you have a write-heavy workload... KV will not be an ideal fit... consider using Durable Objects"). Even at MVP-scale traffic this gives an approximate cap with a real TOCTOU race window, and the vendor's own guidance steers away from this exact use case.
- **Durable Objects — not recommended for this MVP.** Strongly consistent, but an entirely new primitive (new binding type, new local-dev semantics, new billing dimension) for a problem the app's existing Postgres already solves for free. Disproportionate for zero-existing-Cloudflare-bindings app.
- **Postgres/Supabase atomic counter — recommended.** `INSERT ... ON CONFLICT (user_id, window_start) DO UPDATE SET request_count = rate_limits.request_count + 1 RETURNING request_count` is atomic under Postgres MVCC (row lock serializes concurrent increments) in a single round trip — closes the read-then-write race the naive approach has. supabase-js's `.update()` only accepts literal values (no `count = count + 1` expression through PostgREST), so this must ship as a Postgres function invoked via `supabase.rpc(...)`. Fits the project's existing migration convention (`supabase/migrations/YYYYMMDDHHmmss_*.sql`, RLS required per `CLAUDE.md`). Testable today with zero new infrastructure — extend the existing `makeSupabaseStub`/`vi.mock("@/lib/supabase")` pattern already used in the route specs to script an `rpc()` return.
- **Payload-size cap — move the check earlier.** Cloudflare's Workers best-practices docs explicitly recommend enforcing a maximum size _before_ fully reading a body you intend to reject, citing the Workers 128MB memory ceiling. Practical pattern: check `Content-Length` first (cheap, not authoritative — absent under chunked encoding), then stream-and-count bytes via `request.body.getReader()`, aborting once the running total exceeds the cap, **before** calling `.json()`. Platform-level outer ceiling (independent of app code): Cloudflare enforces request body size limits by plan — 100MB Free/Pro, 200MB Business, up to 5GB Enterprise — over which Cloudflare itself returns 413 before the Worker even runs; the app's existing 140M-char (~105MB decoded) schema cap is already close to the Free/Pro platform ceiling, worth noting for the plan. This helper is independently testable in the existing `unit` Vitest project — a plain Node `Request`/`ReadableStream` needs no Cloudflare runtime.

## Architecture Insights

- **Ownership enforcement pattern is consistent and RLS-delegated across both routes**: a `.maybeSingle()` pre-check on the user-scoped client, no explicit `user_id` filter in application code, database RLS does the real work. This is the same pattern §6.4 of the test-plan documents as "the pattern every session-mutation route follows" — Phase 3's new payload/rate-limit checks should slot into the same handler position (after the ownership pre-check, before the LLM call) rather than introducing a parallel gating mechanism.
- **The LLM boundary's "fixed-string error, no upstream leakage" discipline (Phase 2) is a real, load-bearing convention** — both call sites in `llm.ts`, both route wrappers, and the existing contract-test corpus all enforce it uniformly. Any new failure mode Phase 3 introduces (rate-limit-exceeded, payload-too-large) should produce the same shape of error: a fixed, plain-language message, never upstream/internal detail, asserted the same way the existing corpus asserts non-leakage.
- **The project already has a working recipe for testing a new failure branch without new infrastructure**: mock the Supabase client at the network/interface boundary (`vi.mock("@/lib/supabase")` + `makeSupabaseStub`), not the business logic. A Postgres-RPC-based rate limiter fits this recipe directly (script the `rpc()` call's return value); a Cloudflare-binding-based limiter would not (no Miniflare/workerd in the `unit` Vitest project today) — this is a concrete signal for the "likely cheapest layer" column when the plan chooses a mechanism.
- **Two different strictness levels currently exist between the vision and recommendations output paths** (`.data` return vs. `as Recommendation[]` cast) that predate this phase and weren't previously flagged as a Risk #4 concern (the risk is framed around "the vision route" specifically). Worth an explicit scope decision in planning rather than silently picking one up.
